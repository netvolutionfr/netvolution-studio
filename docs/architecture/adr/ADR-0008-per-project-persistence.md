# ADR-0008 — Per-project persistence

**Status:** Accepted on 10/30/2026 · **Date:** 10/30/2026 · **Ref.:** SB-01, SB-06, SB-12, ADR-0004; milestone 2 study §4.4

## Context

ADR-0004 stores standalone documents in `data/documents/` and shared media in `data/media/`. SB-01 requires isolated projects, resources included, and an architecture that lets accounts and organizations in later.

## Recommended decision

1. **One folder per project**: `data/projects/<projectId>/site.json` + `media/` (originals) + `media/.derived/` (rebuildable variants).
2. Project id generated by the server (`p` + 10 `[a-z0-9]` characters), validated by a regex on every request; paths resolved and checked under the root.
3. Routes `/api/projects` (list, create, read, write with `If-Match`, duplicate, delete, archive import/export) and `/media/<projectId>/<file>`.
4. **Deletion = move to `data/trash/`**, after confirmation in the UI. No permanent deletion from the Studio.
5. Duplication: copy of the folder, new id and new name; internal ids (nodes, pages, media) are kept, as they are local to the project.
6. Guards kept: `X-NS-Request`, origin check, listening on `127.0.0.1`, atomic writes, maximum size.
7. Future accounts and organizations: a path prefix in the adapter (`<orgId>/<projectId>`), without changing the model.
8. Milestone 1 documents (`data/documents/`) are imported manually (v1 → v2 migration); no automatic conversion.

## Alternatives

- **Media library shared between projects**: simpler reuse, but contrary to the required isolation and to the standalone export.
- **SQLite database**: useful with several users; out of scope (as in ADR-0004).
- **Immediate deletion**: simpler, but irreversible for an action triggered by a click.

## Consequences

- Replaces point 2 and the "media" addendum of ADR-0004; the rest (ETag, anti-CSRF, visible failures) is unchanged.
- The trash is not emptied automatically; this is documented in the limitations.

## Open points

- [Settled, slice 7] Archive format: a JSON file `{ format: 'ns.archive', version, site, media }` (media in base64), without a ZIP dependency; on import, every file goes again through the upload checks (type, size, signature, SVG policy).

## Addendum — implementation (slice 2, 10/30/2026)

- The site id is the project id; the server imposes it on creation and duplication.
- Creation (`POST /api/projects`) receives a complete site (template or import, v1 accepted) and copies the referenced
  media from the read-only sources; missing media are counted (`missingMedia`).
- `PUT` requires `If-Match`; there is no more creation through `PUT`. The `/api/documents` and `/api/media` routes of
  milestone 1 are removed.
- The Studio serves media at `/media/<projectId>/<file>` and passes this prefix to rendering (`RenderContext.mediaBase`);
  the export keeps `/media/<file>`.
