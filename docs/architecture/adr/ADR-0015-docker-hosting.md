# ADR-0015 — Hosting the Studio: Docker, nginx and external access protection

**Status:** Accepted on 10/30/2026 · **Date:** 10/30/2026 · **Ref.:** CLAUDE §3 and §8, ADR-0004, ADR-0008, ADR-0014, ADR-0016

## Context

The Studio could only be used locally. Its API (ADR-0004, ADR-0008) ran in the Vite development server, on 127.0.0.1. We want to make it available at `https://studio.netvolution.fr`, on the web4 server (Debian 13), with these constraints:
- **password access**;
- no Node dependency installed on the server;
- automatic deployment from GitHub, as for the other Netvolution applications.

The Studio has no authentication, and CLAUDE §8 forbids inventing one: "for an Internet deployment before the product has authentication, use a proven external access protection".

## Decision

1. **Production server** (`apps/studio/server.ts`):
   - it serves the compiled application and the same API (`createApi`) on a single port, without Vite;
   - data is in `NS_DATA_DIR`, exports in `<data>/exports`;
   - it has no authentication and must never be exposed directly.
2. **Docker image** in three stages:
   - build;
   - runtime dependencies only;
   - final Alpine `node` image, with the version pinned.

   The image runs as an unprivileged user. It contains npm and tar, needed by the export (Astro build, archive), and a healthcheck. Data is in the `/data` volume.
3. **Container published on `127.0.0.1` only**, managed by `compose.yaml`.
4. **nginx in front**:
   - HTTPS (Let's Encrypt);
   - **HTTP Basic authentication** on the whole site, with bcrypt-hashed passwords;
   - rate limiting, and fail2ban advised;
   - `noindex`;
   - long timeouts for the export.
5. **Downloading exports**: `GET /api/exports/:name.tar.gz` (sources or static site, without `node_modules`). Paths on the server are useless from a remote browser.
6. **GitHub Actions CI/CD**:
   - checks (typecheck, lint, tests), also on every pull request;
   - image pushed to GHCR, tagged by commit;
   - deployment over SSH: `docker compose pull && up -d` with the commit's image, then waiting for a healthy state.

   The secrets (SSH, GHCR token) are in GitHub. The AI keys are in the server's `.env`, mode 600, never in the image.
7. **Versions and supply chain**: the details are in `deploy/README.md`.
   - Node 26 LTS in the image, with its version and checksum pinned, and Alpine patches on every build.
   - CI on Node 26 and 24, at the latest patch, with a blocking npm audit (high and critical vulnerabilities).
   - Actions pinned by commit and updated by Dependabot (actions, image, npm).
   - Image published with provenance and SBOM; SSH host key checked on deployment.

## Alternatives

- **Node installed on the server, with systemd**: simpler, but refused (version dependency on a server shared with other sites).
- **Authentication in the Studio**: out of scope and contrary to CLAUDE §8 until it is designed (roles, passkeys, audit).
- **Identity portal (Authelia, Cloudflare Access, oauth2-proxy)**: two-factor authentication and named accounts, but one more component to operate. Recommended if the number of users grows. It sits in front of the same container, without changing the Studio.
- **Building exports in a separate container**: better isolation of the npm dependencies of exported sites, but more complex. To reconsider if the export becomes a shared service.

## Consequences

- Anyone who knows a password has **full rights**: there are no roles and no per-user log.
- Designed for one user at a time per project: a concurrent save is refused (conflict).
- **The export runs `npm ci` and `astro build`** in the container, with access to the npm registry. Dependencies come from the export's pinned lockfile, generated by the Studio and not by the user. The build runs without privileges, in the container.
- Backups of the `data/` folder belong to the server's operations.
